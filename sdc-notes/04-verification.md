2211 assertions, all passing, 12 s.


## 1. Coefficients checked against qmat, value by value

`lib/OrdinaryDiffEqSDC/test/sdc_reference.jl` holds nodes, weights, `Q` and
seven `Q_Δ` matrices generated by `qmat` itself
(`sdc-notes/tools/gen_reference.py`, run against a fresh clone of
`Parallel-in-Time/qmat`). The Julia generators are asserted equal to them at
`atol = 1e-13`.

Coverage: 6 node configurations × 7 sweepers = 42 `Q_Δ` matrices, plus 6 node
sets, weight vectors and `Q` matrices.

| `M` | node type | quadrature type |
|---|---|---|
| 4 | Legendre | Gauss |
| 2 | Legendre | Radau-left |
| 3 | Legendre | Radau-right |
| 3 | Legendre | Lobatto |
| 4 | equidistant | Radau-left |
| 3 | equidistant | Lobatto |

Sweepers: `:BE`, `:FE`, `:Trapezoid`, `:LU`, `:Picard`, `:BEpar`, `:MIN_SR_NS`.

This is the check that matters most, because it removes the entire class of
"my quadrature matrix is subtly different from theirs" errors before any
convergence result is interpreted. Two real bugs were caught by it and by the
invariant tests around it:

* `Q` was built as `C V⁻¹` with the Vandermonde transposed, so `Q·1 ≠ τ` and
  every measured order came out as 0. Caught by `sum(weights) == 1`.
* Weiser's LU sweeper threw `SingularException` for Lobatto and Radau-left,
  where `τ₁ = 0` makes `Q`'s first row vanish. `scipy.linalg.lu`, which `qmat`
  uses, does not check for singularity, and the zero pivot is the *correct*
  answer there — it makes the first node explicit, which is right because
  `u(τ₁) = u_n`. Fixed with `check = false`.

Independent of `qmat`, the tableaux are also checked against their defining
identities for `M = 2…6` on every node/quadrature combination: `Q τⁿ = τⁿ⁺¹/(n+1)`
and `Σ w_j τ_jⁿ = 1/(n+1)` for `n = 0 … M−1`, `Q_Δ` lower triangular, backward
Euler row sums equal to `τ`, `Q_Δ` diagonal for the diagonal sweepers, and
`Q_Δ^{TRAP} = (Q_Δ^{BE} + Q_Δ^{FE})/2`.

## 2. The order gate

Mirrors `qmat/tests/test_qdelta/test_timestepping.py`
(`testSDCConvergenceQUADRATURE` / `testSDCConvergenceLASTNODE`) exactly: Dahlquist
`u' = iu` on `[0, 2π]`, `u₀ = 1`, three step sizes chosen by the theoretical
order, `L∞` error over the step solutions, least-squares slope against `log Δt`,
accept if the regression residual is below `0.05` and the slope is within `0.5`
of the prediction. Step-size triples and tolerances are `qmat`'s.

**470 combinations** are in the committed gate: `M ∈ {2,3,4}` × node types
`{Legendre, equidistant}` × quadrature types `{Gauss, Radau-left, Radau-right,
Lobatto}` × sweepers `{BE, FE, Trapezoid, BEpar}` × `K ∈ {1,2,3}` with the
quadrature update and `K ∈ {1,2,3,4}` with the last-node update. **All 470
pass.** Runtime for the whole sweep is 0.8 s.

How the 470 were selected: I ran the identical sweep in Python against `qmat`
first, over 480 combinations. 470 satisfy `qmat`'s own tolerance. The 10 that do
not are exactly the cases `qmat`'s test file special-cases with hand-written
`nSteps` overrides — all `BEpar`: two at `K = 3` with the quadrature update
(Legendre/Radau-right `M = 2`, equidistant/Radau-right `M = 3`) and eight at
`K = 4` with the last-node update. I excluded those rather than reproduce the
overrides, and noted it here rather than silently.

### `alg_order` versus `qmat`'s predictor

`alg_order` implements the base rule only: one order per sweep, two on the first
sweep for a second-order sweeper, plus one for the quadrature step update, capped
at the collocation order. `qmat`'s `getOrderSDC` adds roughly 143 hand-tabulated
bonus cases on top.

Over the 470 gated rows: **457 agree exactly**, and **13 are bonus cases** where
`qmat` predicts one to two orders more than the base rule. On those 13 the test
asserts `alg_order(alg) < expected` — i.e. our prediction is a documented strict
lower bound — and still requires the *measured* order to match `qmat`'s higher
number. Eleven of the 13 use the last-node update (ten `:Trapezoid`, one `:FE`);
the other two are equidistant/Radau-left with the quadrature update, `:Trapezoid`
at `K = 1` and `:BEpar` at `K = 3`.

Three things worth pointing out.

* The collocation ceiling is real and is reached: `M = 4` Radau-right with `K = 6`
  gives 6.79, against a ceiling of `2M − 1 = 7`. Adding sweeps past that does
  nothing.
* Equidistant nodes cap out at `M`, as expected: `M = 3`, `K = 3` gives 2.98 where
  the same configuration on Legendre nodes gives 3.87.
* `:MIN_SR_NS` gains **two** orders per sweep here, not one. That reproduces the
  observation in Čaklović et al. (§3.1, Figure 2) that this preconditioner does
  better than the theory predicts and that the authors have no explanation for
  it. `:LU` and `:MIN_SR_NS` are therefore gated as a lower bound in the test
  suite, not an equality.

## 3. Negative controls

The gate above can only pass. These establish that it is measuring what it is
supposed to. `M = 3`, Legendre/Radau-right, `:BE`, `K = 3`, quadrature update;
predicted order 4.

| perturbation | measured order | residual |
|---|---|---|
| none (baseline) | 3.872 | 0.011 |
| `Q[2,1] += 1e-3` | **2.119** | 0.090 |
| `Q[2,1] += 5e-2` | **1.024** | 0.005 |
| `weights[1] += 1e-3` | **0.385** | 0.041 |
| `QΔ[2,2] += 5e-2` | 3.839 | 0.013 |
| `QΔ[2,1] += 5e-2` | 3.872 | 0.011 |
| `K = 2` instead of 3 | 2.970 | 0.003 |

The perturbations are applied to the live tableau inside the integrator
(`init`, mutate `integrator.cache.tab`, `solve!`), so they go through the real
`perform_step!`, not a reimplementation.

Reading the table:

* Corrupting `Q` by `10⁻³` — three orders of magnitude smaller than the
  discretisation error at the coarsest step — drops the order from 4 to 2.1.
  A larger perturbation takes it to 1.0. The gate is sensitive to `Q`.
* Corrupting a step-update weight is worse still: order 0.385. The weights are
  the other half of the collocation rule.
* **`Q_Δ` is different, and this is the control on the controls.** Perturbing the
  preconditioner — diagonal entry or strictly-lower entry — leaves the order at
  3.84/3.87, indistinguishable from baseline. That is not a weakness of the test,
  it is the theory: `Q_Δ` cancels at the fixed point of the sweep, so it can only
  change how fast the iteration converges, never what it converges to. If this
  row had *also* moved, the three rows above it would be telling me nothing more
  than "the test notices when I change a number".
* Removing one sweep removes exactly one order.

I also confirmed all seven rows independently in Python against `qmat` before
running them in Julia, and the two agree to within the noise of the fit
(e.g. `Q[2,1] += 1e-3` gives 2.119 in both).

## 4. Non-linear problems

The linear gate cannot see an error in how the per-node right-hand side is
assembled, only in the coefficients. Two non-linear problems with exact
solutions, both using the automatic-differentiation Jacobian path rather than a
supplied one:

* **Scalar Riccati**, out-of-place: `u' = −u²`, `u(0) = 1`, exact `1/(1+t)`, on `[0, 2]`.
* **2-D system**, in-place: `u₁' = −u₂ − r u₁`, `u₂' = u₁ − r u₂` with
  `r = u₁² + u₂² − 1`, exact `[cos t, sin t]` on `[0, 2]`. The extra term
  vanishes on the solution but not in the Jacobian, so the problem is genuinely
  non-linear and stable (both eigenvalues `−1` at `t = 0`).

| problem | sweeper | `K` | predicted | measured | residual |
|---|---|---|---|---|---|
| Riccati (out-of-place) | `:BE` | 1 | 2 | 1.997 | 0.0003 |
| Riccati | `:BE` | 2 | 3 | 2.816 | 0.0071 |
| Riccati | `:BE` | 3 | 4 | 3.582 | 0.0194 |
| Riccati | `:BE` | 4 | 5 | 4.284 | 0.0339 |
| 2-D (in-place) | `:BE` | 2 | 3 | 2.837 | 0.0067 |
| 2-D | `:BE` | 3 | 4 | 3.751 | 0.0109 |
| 2-D | `:BE` | 4 | 5 | 4.705 | 0.0096 |
| 2-D | `:Trapezoid` | 2 | 4 | 4.052 | 0.0182 |
| 2-D | `:LU` | 3 | 4 | 3.761 | 0.0106 |
| 2-D | `:FE` (fully explicit sweep) | 3 | 4 | 3.998 | 0.0000 |

The order survives outside the linear test case. The measured values sit a little
below the prediction at high `K` because `Δt ∈ [1/16, 1/4]` on these problems is
not yet deep in the asymptotic regime — the Riccati `K = 4` row (4.284 against 5)
is the clearest case, and it is why the committed test only asserts equality up
to `K = 3` there and uses a lower bound elsewhere. I did not tune the problems to
make the numbers prettier.

The `:FE` row is a separate structural check: with a strictly lower triangular
`Q_Δ` no nonlinear solver is built at all (`solver_index` is all zeros) and the
sweep runs fully explicitly. Same order behaviour, different code path.

A final consistency check asserts that the in-place and out-of-place
implementations agree to `rtol = 1e-10` on the same problem.

## 5. Work per step

`u' = [−u₂, u₁]`, 16 fixed steps, `M = 4`, `K = 4`:

```
nf = 1090   nsolve = 514   nw = 256   njacs = 256
```

`256 = 16 steps × 4 nodes × 4 sweeps`. One Jacobian evaluation and one `W`
factorisation per nonlinear solve, where the design intends one per node per
step. The cause is `do_newJW` in
`lib/OrdinaryDiffEqDifferentiation/src/derivative_utils.jl:534`:

```julia
!integrator.opts.adaptive && return true, true # Not adaptive will always refactorize
```

which is library-wide policy for fixed-step implicit solves, not something SDC
does. `ImplicitEuler` with `adaptive = false` shows `njacs = 16` for the same 16
steps — one per step, because it has one solve per step. Analysis and the fix in
`02-nonlinear-solver-reuse.md` §3.

## 6. Ecosystem check

* **General registry**: no registered Julia package implements SDC. I grepped all
  12 249 `Package.toml` names in `~/.julia/registries/General` for `sdc`,
  `deferred`, `spectral`, `pfasst`, `parallelintime`, `collocation`, `paradiag`,
  `parareal`. The hits are unrelated (`SpectralClustering`, `CollocationIRK`,
  `ParaReal`, `TimeParallel`).
* **GitHub**: four Julia SDC repositories exist, none registered.
  `lisawim/SpectralDeferredCorrections.jl` is the live one — Lisa Wimmer is a
  pySDC contributor, it was last touched 2025-04-17, and its own README describes
  it as "only a playground to learn Julia yet". `leespen1/SpectralDeferredCorrection`
  and `leespen1/SDC.jl` are abandoned 2021 experiments; `janEbert/sdc-rl-jl` is a
  reinforcement-learning study that uses SDC rather than providing it.
* **This repository**: `grep -ri "spectral deferred\|deferred correction"` over
  all `.jl` and `.md` files returns nothing. Nothing to reuse and nothing to
  collide with.

**So Fynn's claim needs one qualification, not a correction:** nobody is building
SDC *in the Julia ODE ecosystem* — there is no registered package and nothing in
DifferentialEquations.jl — but someone inside the parallel-in-time community is
prototyping a standalone Julia SDC package. Worth mentioning to him, since she is
in the adjacent group.

### Quadrature nodes: dependency or not

The question was whether to use `FastGaussQuadrature.jl` or compute nodes from
scratch. Both are defensible; here is the trade-off and what I picked.

**For `FastGaussQuadrature.jl`:** it is already a dependency of
`lib/OrdinaryDiffEqFIRK` in this very repository, so it introduces no new
ecosystem risk and no precedent argument to win. It is maintained by
JuliaApproximation, it is small (LinearAlgebra, SpecialFunctions, StaticArrays),
and its `gausslegendre` is Bogaert's `O(n)` algorithm — far better than anything
I would write, and accurate to machine precision at `n = 10⁶`.

**Against:** SDC needs `M ≤ ~12` nodes, where none of that sophistication
matters. More importantly, in the version resolved here (1.1.0) `gausslegendre`
and `gausslobatto` are `Float64`-only — `gausslegendre(n::Integer)` is the sole
method — so a `BigFloat` problem would silently get `Float64`-accurate nodes.
(`lib/OrdinaryDiffEqFIRK/src/firk_tableaus.jl:378` calls `gausslegendre(T, n)`,
which does not match any method in that version; either FIRK resolves a different
version or that path is untested.) SDC also needs Radau-left, Radau-right *and*
Lobatto on `[0,1]`, so there would be wrapping and re-mapping code either way.

**Chosen: compute them natively.** Interior nodes are roots of Jacobi
polynomials — `P^{(0,0)}_M` for Gauss, `P^{(0,1)}_{M-1}` and `P^{(1,0)}_{M-1}` for
the two Radau families, `P^{(1,1)}_{M-2}` for Lobatto — found by grid bracketing
plus bisection. About 60 lines, no derivative needed, generic in the element type,
and the accuracy question is settled by the `atol = 1e-13` comparison against
`qmat` and the `Q τⁿ` identities in `BigFloat`. Switching to
`FastGaussQuadrature.jl` later is a one-function change if that is preferred; the
golden-value test would catch any difference immediately.

That decision did produce one bug, which is worth recording because it would bite
anyone writing this code: `P₃(0)` evaluates to `-0.0`, so `signbit` reported a
sign change across a bracket whose endpoint *was* the root, and `BigFloat`
bisection towards an exact zero never terminates — there is no smallest normal,
so the midpoint halves through the entire exponent range. It hung, it did not
error. Fixed by detecting exact roots on the grid and by bounding the bisection.

## 7. What is not verified

* **No stiff problem is in the gate.** Every convergence result above is on a
  non-stiff or mildly non-linear problem. SDC's stiff behaviour — where the choice
  of `Q_Δ` actually matters, and where `:LU` should beat `:BE` decisively — is
  untested. This is the largest gap.
* **No stability regions computed.** I have not reproduced the stability-domain
  plots from Čaklović et al. §3.2, so I cannot claim anything about A-stability
  of any configuration here.
* **No allocation or JET/Aqua QA tests.** `lib/OrdinaryDiffEqMultirate` has an
  `AllocCheck` suite; SDC does not yet.
* **`Float32` and `BigFloat` problems are untested end to end.** The *tableaux*
  are checked in `BigFloat` (`Q τ³ = τ⁴/4` to better than `10⁻⁴⁰`); a full solve
  in another precision is not.
* **Dense output**: `sol(t)` returns values, but the cache reports
  `get_fsalfirstlast = (nothing, nothing)` (following `PDIRK44`), so the
  interpolation is whatever the core falls back to and its order is not verified.
  The natural interpolant — the collocation polynomial through the node values —
  is free and unimplemented.
* **Mass matrices and DAEs** are untouched.
